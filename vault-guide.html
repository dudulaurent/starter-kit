Vault Guide

How a personal knowledge vault is built, folder by folder, and how the pieces link. A vault is a folder of markdown files that an AI coding agent (Claude Code or Codex) maintains for you. Nothing in this page is personal: the example agents are invented.

The big picture

One folder is the hub. Inside it, each area of your life or work gets an agent: a sub-folder with its own instructions, notes, current state and follow-ups. Bigger software projects sit beside the vault with their own repository.

The vault Agent inside the vault Peer project (own repo) Shared framework (optional)

The five ideas that hold it together

  1. Files, not memoryThe agent does not remember yesterday. The vault is its memory: every session reads files at the start and writes files at the end.
  2. One folder, one jobEach agent has a single purpose and its own instructions. Opening the agent in that folder is what makes it play that role.
  3. Three homes for factsAbout one item, true right now, or a lesson that held twice. Each goes to a different file and none of them grows forever.
  4. The agent writes, you talkYou describe, decide and approve. The agent edits the files. The most important files change only after your yes.
  5. Question before buildingAnything new is first challenged against your own vocabulary and past decisions, so the vault stays consistent as it grows.

AGENTS.md

Loaded every session

The constitution. Says what the vault is, which agents are active, where identity lives, and the behaviour rules that bind everyone: the agent writes and the human talks, confidentiality, ask before changing major files, question new ideas first.

Written
Rarely, with your yes
Keep out
Anything that changes weekly

vault-config/session-context.md

Read by start and end

Lets two generic routines serve your vault. It says what you call a work item, where boards and dashboards live, and what extra checks to run.

Written
When you add an agent or change a name

Routines

You type them, the agent can too

session-start loads state. session-end saves it. lint-vault is the weekly health check and the gate for spreading patterns. Type /session-start in Claude Code or $session-start in Codex.

Written
Rarely, when a routine falls short

Skills folders

One copy per tool

Reusable ways of working that the agent applies when the task matches. grill-with-docs is the first one: it interviews you before anything new is built.

Difference
A command is a routine you can type by name, a skill is a helper the agent picks. Both are skills in the tools. Each tool reads its own folder, so the files exist twice

me/

Source of truth about you

identity.md holds background and values. profile.md holds experience with evidence, the base for any CV or bio. preferences.md holds how you like to work.

Written
Only after your explicit yes

dashboard.md (root)

The vault index

A short table: which agents are active, where each dashboard is, what blocks across them. It stays tiny so loading it costs almost nothing.

Never holds
Anything about an agent's own domain

wiki/ (root)

Vault-wide knowledge

CONTEXT.md is the glossary. adr/ keeps one file per hard-to-reverse decision. patterns.md is the registry of habits worth spreading between agents.

Written
As terms and decisions are resolved

Loose ends

A thread is one open follow-up as one small file. An idea is a seed that may later become an agent after a grill session.

How it is linked

Three kinds of link make the vault hang together: instructions that stack, files that every agent reads, and wiki links that connect notes. Nothing is automatic except the loading of instruction files. Everything else is a rule the agent follows because a file tells it to.

The three kinds of link

Instruction stacking

Automatic

Codex loads AGENTS.md from the project root down to the folder you open. Claude Code loads CLAUDE.md the same way, and each one-line CLAUDE.md forwards to its AGENTS.md. So an agent folder gets its own rules plus the root rules. Identity and voice reach every agent because the root file tells the agent to read them at the start of each session.

Read-order links

Written as arrows in AGENTS.md

The agent's AGENTS.md lists what to read and where, for example identity, dashboard, last session, threads. These are plain relative paths. They are instructions, so the agent follows them rather than the computer enforcing them.

Wiki links

For you and for the agent

Notes link to each other with double brackets, for example [[patterns]]. Obsidian turns them into clickable links and a graph. The agent uses them to find related notes. Every wiki file should be linked from the agent's hub, or it becomes an orphan nobody reads.

Where each kind of fact goes (the three homes)

  1. About one itemThe item's own file in items/done/. Answers: what happened with this one?
  2. True right nowOne line on the dashboard. Answers: what is the state? When the item closes, the line is deleted.
  3. A lesson that held twiceThe agent's wiki/patterns.md. Answers: have we met this before? One occurrence is only a thread.
Why this matters. Without the rule, the dashboard becomes a diary. A dashboard that keeps growing costs more to load every session than the work it supports.

A session, step by step

Every working session has three beats. The two ends are commands you type. In the middle you simply work.

What session-start does

  1. Detects the session type. Inside an agent folder it is an Agent Session. At the vault root it is a Root Session.
  2. Loads state. The vault index, then the agent's dashboard, last session, patterns and item board. It never reads another agent's dashboard.
  3. Reconciles. Runs git fetch and looks at recent changes. If you or a second session edited agent files since last time, the agent reads them before writing anything. It also lists branches that hold finished but unmerged work.
  4. Loads the wiki hub so it knows what knowledge exists.
  5. Scans threads and items for anything overdue or blocking.
  6. Runs agent-specific checks if the agent's AGENTS.md defines some.
  7. Prints a short summary and does no other work until you read it.

What session-end does

  1. Fetches again to see what other sessions landed.
  2. Runs the agent's own end steps.
  3. Updates the dashboard. Finished work is deleted, new work is added, nothing is appended as a recap.
  4. Writes history to the right home. Applies the three homes rule, including to old entries it finds.
  5. Overwrites last-session.md with a short summary and numbered priorities. If another session wrote it meanwhile, it appends a labelled section.
  6. Creates or closes thread files.
  7. Checks the grill checkpoint if one ran: were terms and decisions recorded?
  8. Commits the exact files touched, on the session's own branch. Never stages everything at once.
  9. Confirms which files changed, so you can verify without opening each one.

When the agent must ask before writing

  1. Major filesRoot AGENTS.md, me/profile.md and me/identity.md. The agent shows the exact change first.
  2. PatternsA habit that could help other agents is proposed to you. Only after your yes does it enter the registry.
  3. Story driftIf what you say differs from your saved story, The agent asks instead of quietly updating.
  4. Main branchNothing is merged or pushed to main without your explicit yes in that session.

Two sessions at once

A session cannot know whether another is running, so the safe habits are always on. Each session works on its own branch. Files are staged by name, never all at once. The two files rewritten every time (the dashboard and last session) are re-read before editing. For truly parallel work, give the second session its own worktree, which is a second working copy of the same repository.

Growing it

Start with the vault and one agent. Add each of these only when you feel the need.

First

An ops agent

no code

An agent that works through notes, skills and commands only. A job search, a reading list, a research topic, a business log. Its work item is whatever you track: an application, a paper, a client.

Needs
AGENTS.md, dashboard, items, threads, wiki
Created by
A grill session at the vault root
Second

A code agent

owns software

An agent that builds and maintains an application. Adds a tickets board, a build-context file and a build routine split into roles, so design, building and testing are separate steps with separate mindsets.

Roles
UX, UI design, architect, developer, infrastructure, quality check
Work item
Ticket
When it has a remote

A peer project

own repo

A project that pushes to its own remote lives beside the vault, not inside it. The test is mechanical. The vault index lists it and points to it, and never loads its dashboard.

Why
Keeps each repo small and keeps private material out of public ones
When two repos share routines

A shared framework

plugins

A separate repository packaged as plugins for your tool. One layer holds identity-free mechanics (session routines, build roles). A second layer holds what is personal (your voice, your story). Projects install the layers they need.

Test for the split
Would this file read identically for another person? Then it is identity-free
When habits are stable

Guards

hooks

Small programs that run before an action and refuse it if it breaks a mechanical rule, for example pushing to main or staging every file at once. A written rule relies on the agent remembering. A guard does not.

Fail style
Closed for actions hard to undo, open with a warning for reversible ones
When the vault is big

An atlas page

optional

One standalone HTML file that draws the structure so a newcomer, or you in six months, can see it at once. Structure only: no private content, no figures, no outcomes.

Refresh
On request, never automatically

A growth path that works

  1. Week 1: identity files, root rules, the two session commands, one ops agent.
  2. Weeks 2 to 3: use the loop daily. Fix the commands where they fall short.
  3. Month 2: second agent. First patterns proposed and approved. First weekly lint.
  4. Later: a code agent or a peer project, then a shared framework once two repos need the same routine.

Words and decisions

The vocabulary the vault uses, and the design choices behind its shape. Reuse the words as they are. A shared vocabulary is what lets the agent and you mean the same thing.

Design choices and the reason for each

Structure

  • Dashboards per agentOne live-state file per agent, with a thin index above. A single big dashboard grows until it is too costly to load.
  • Peers by remoteA project with its own remote lives beside the vault. The test needs no judgment.
  • No app on topA web view over the vault was built once and never used. The markdown files are the interface.

Memory and history

  • Threads as filesOne follow-up per file with frontmatter beats one long list nobody trims.
  • Three homesFacts are filed by kind. A running log file was retired because nothing ever read it.
  • last-session overwrittenContinuity without accumulating history.

Working method

  • Grill before buildingQuestions come first, files second. It catches naming clashes before they spread.
  • Commits at session endOne explicit commit step, not automatic hooks, so nothing is saved half-finished.
  • Patterns through a gateA habit spreads to other agents only after you approve it.
  • Inventory, not enforcementThe weekly lint reports drift from shared files. It never forces a change.

Vocabulary

Vault

The root folder holding all agents, shared rules and the owner's identity files.

Agent

A named area inside the vault with one job, its own AGENTS.md, wiki, dashboard and threads.

Ops agent

An agent with no code. Works through notes, skills and commands.

Code agent

An agent that owns software and uses tickets and a build routine with separate roles.

Root session

The agent opened at the vault root. For vault-wide work such as adding an agent or running the weekly lint.

Agent session

The agent opened inside one agent folder. It sees that agent's domain plus the shared rules.

Instruction file

The file holding the rules for the vault or one agent, loaded by the tool on its own: AGENTS.md, with a one-line CLAUDE.md beside it for Claude Code.

Command

A named routine you can start by typing its name, such as session-start. The agent may start it too.

Skill

A reusable way of working that the agent chooses when the task matches.

Rule

An always-on instruction file, such as the voice guide.

Wiki

The structured notes inside one agent: a hub page, reference files and decisions.

Dashboard

One file per agent showing only what is true right now.

Vault index

The root dashboard. A short list of active agents and anything blocking.

Work item

The unit an agent tracks. Each agent gives it its own name: ticket, application, task.

Thread

One open follow-up saved as its own small file under threads/active/.

Three homes

The rule for where a fact is saved: the item's file, the dashboard, or the patterns file.

Pattern

A habit that held twice. In the root registry it is a proposal to spread to other agents, after approval.

Pattern registry

wiki/patterns.md at the vault root. The approved list of patterns and which agents adopted each one.

CONTEXT.md

The glossary. Words only, no implementation detail.

ADR

Architecture decision record. One short file explaining a hard-to-reverse choice, why it was made and what it costs.

Raw

Source documents stored as received and never edited afterwards.

Narrative drift

When what you say now differs from what the vault holds about you. The agent asks before changing the saved version.

Peer project

A project with its own repository placed beside the vault. The vault points to it and never loads it.

Plugin

A packaged set of commands, roles and rules that can be installed in several projects.

Guard

A hook that blocks a mechanical rule break before it happens.

Worktree

A second working copy of the same repository, used so two sessions do not overwrite each other.

Atlas

A single HTML page that draws the vault's structure.

Set up yours

Two ways to the same vault. Pick the one that fits how you like to work.

Path A

Template folder

faster

Copy the vault-template/ folder, run git init, open Claude Code or Codex in it and let the agent walk you through each placeholder, one question at a time. You get the full skeleton at once and fill it in.

Good if
You already know what the vault is for
Time
One sitting for the skeleton, then daily use
Path B

Staged setup guide

guided

Give SETUP.md to your agent in an empty folder. It interviews you and builds in seven stages, keeping a progress file so you can stop and resume in later sessions.

Good if
You would rather be interviewed than edit templates
Time
Several short sittings

The seven stages of Path B

  1. 0 OrientationYour name, language, and what the vault is for.
  2. 1 IdentityThe three me/ files and your voice rules.
  3. 2 SkeletonFolders, root rules, session commands, glossary.
  4. 3 First agentA grill session, then the agent folder.
  5. 4 Prove the loopReal work, then session-end, then inspect.
  6. 5 GrowMore agents, code agent, peers, framework, guards.
  7. 6 ShareOptional atlas page, structure only.
Start small. Most of what makes this work is the daily start and end routine. A single agent used for a month teaches more than five agents set up in a weekend.
